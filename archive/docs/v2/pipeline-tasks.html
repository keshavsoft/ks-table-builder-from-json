1. What Is a Pipeline Task?

A pipeline task is a small transformation function that receives the current JSON specification and returns the transformed specification. 

Input Specification
        |
        v
Pipeline Task
        |
        v
Output Specification

The task operates on the JSON specification. It does not need to create DOM elements.

2. The Basic Task Contract

Every task follows the same fundamental contract: 

({ inSpec }) => {
    return transformedSpec;
}

Conceptually: 

Spec -> Task -> Spec
The task receives a specification and must return a specification.

3. Why Tasks Are Small

Each task should ideally have one clear responsibility.

Task Responsibility
Theme Task Apply theme information to the specification.
Header Task Transform the header portion of the specification.
Body Task Transform the body portion of the specification.
Footer Task Transform the footer portion of the specification.
Serial Task Transform the serial-column representation.
Custom Task Provide an extension point for additional transformations.

4. Task Factory Pattern

The Table tasks are created through factory functions. 

createApplyThemeTask(...)
createHeaderTask(...)
createBodyTask(...)
createFooterTask(...)
createSerialTask(...)

The factory receives configuration and returns a configured transformation function. 

Configuration
      |
      v
Task Factory
      |
      v
Configured Task
      |
      v
Pipeline

5. Why Use a Factory?

Consider a Header Task. 

createHeaderTask({
    inShowHeader: false
})

The returned function already knows the configuration it needs.

The pipeline runner only needs to provide the current specification. 

taskFn({
    inSpec: currentSpec
})

The generic runner does not need to understand inShowHeader.

6. Theme Task

The Theme Task is responsible for applying the resolved theme specification to the current specification. 

createApplyThemeTask({
    inThemeSpec
})

The task delegates the actual recursive operation to applyTheme(). 

({ inSpec }) => {

    if (!inThemeSpec) {
        return inSpec;
    }

    return applyTheme({
        inSpec,
        inThemeSpec
    });
}

The output remains a JSON specification.

7. Theme Task Flow

God Spec
    |
    v
createApplyThemeTask()
    |
    v
applyTheme()
    |
    v
Themed Spec

No DOM is created during this operation.

8. Header Task

The Header Task receives the header visibility configuration. 

createHeaderTask({
    inShowHeader
})

The task then transforms the current specification according to that configuration. 

inShowHeader = true
        |
        v
Header remains available
        
inShowHeader = false
        |
        v
Header is transformed according to task rules

The task is concerned with the specification. DOM materialization happens later.

9. Body Task

11. Serial Task

The Serial Task represents a UI-specific Table transformation. 

createSerialTask({
    inShowSerial
})

A serial column is not necessarily part of the application's original column definition.

It can be introduced as a UI concern through the transformation process. 

Original Columns
       |
       v

       |
       v
UI Columns

12. Custom Tasks

Custom tasks provide an extension mechanism. 

Built-in Tasks
      |
      +-- Theme
      +-- Header
      +-- Body
      +-- Footer
      +-- Serial
      |
      +-- Custom Task
      |
      v
Final Pipeline

A custom task can modify the specification without requiring changes to the generic pipeline runner.

13. Example Custom Task

A custom task can follow the same contract: 

const addOptionsTask = ({ inSpec }) => {

    const localSpec = inSpec;

    // Transform the specification.

    return localSpec;
};

The task can then be supplied as part of the custom task array. 

{
    inCustomTasks: [
        addOptionsTask
    ]
}

14. Task Ordering

Tasks execute in the order in which they appear in the pipeline. 

Task A
   |
   v
Task B
   |
   v
Task C
   |
   v
Task D

Task B receives Task A's result. Task C receives Task B's result. Task D receives Task C's result.

15. Why Ordering Matters

A later task may depend on changes made by an earlier task. 

Task A
 |
 +-- inserts node
 |
 v
Task B
 |
 +-- modifies inserted node

If the order is reversed, Task B may not find the node it expects.

Pipeline order is therefore part of the component's transformation contract.

16. Tasks Should Avoid DOM Operations

A specification transformation should preferably not contain: 

document.createElement()
appendChild()
querySelector()
classList.add()
addEventListener()

Those operations belong to the DOM layer.

A task should instead modify: 

tagName
attributes
properties
children
text
events

inside the specification.

17. Example: Adding a Specification Node

Suppose a task needs to add a button.

The task should conceptually add: 

{
    "tagName": "button",
    "attributes": {
        "type": "button"
    },
    "textContent": "Options"
}

It should not directly execute: 

document.createElement("button")

The recursive DOM builder will perform that materialization later.

18. Task Composition

Small tasks can be composed into larger behavior. 

Theme Task
     +
Header Task
     +
Body Task
     +
Footer Task
     +
Serial Task
     |
     v

This is easier to reason about than one enormous transformation function.

19. Task Independence

Tasks should ideally avoid knowing unnecessary details about unrelated tasks. 

Theme Task
    |
    +-- knows about theme

Header Task
    |
    +-- knows about header

Serial Task
    |
    +-- knows about serial

The pipeline provides the coordination between them.

21. Task Factories and Closures

A task factory can capture its configuration through a closure. 

const createTask = ({ option }) => {

    return ({ inSpec }) => {

        // option is available here.

        return inSpec;
    };
};

This means the generic pipeline runner does not need to know about the task's configuration.

22. Task Naming

Task names should communicate what specification concern they transform. 

createHeaderTask()
createBodyTask()
createFooterTask()
createSerialTask()
createApplyThemeTask()

This makes the pipeline readable by inspection.

33. Forms Can Use the Same Task Model

A Form can have its own task factories. 

createFormThemeTask()
createFieldTask()
createLabelTask()
createButtonTask()
createValidationTask()

These tasks can be executed by the same generic runPipeline().

The component-specific tasks differ. The pipeline mechanism does not.

Some tasks may eventually become reusable across components.

For example:

36. Task Purity

A useful design goal is to keep transformations as predictable as possible. 

Same Input
    +
Same Configuration
    |
    v
Same Output

The closer a transformation is to this model, the easier it is to test and reason about.

37. Mutation vs Replacement

A task may internally choose how it constructs its result. The architectural requirement is that it returns the correct specification. 

Input Spec
    |
    v
Transformation
    |
    v
Returned Spec

Whether internal implementation mutates or reconstructs parts of the object is an implementation detail.

The important contract is the pipeline's specification flow.

38. Error Handling

Tasks should handle invalid configuration appropriately rather than allowing malformed values to silently corrupt the specification.

The generic runner should remain simple and should not need to understand every possible component-specific validation rule. 

Component Validation
        |
        v
Configured Task
        |
        v
Generic Runner

39. Pipeline Extension Without Core Changes

One of the strongest benefits of the design is that a new transformation can be introduced without changing: 

runPipeline()
buildSpecElement()
domElementBuilder()

Only the component pipeline needs to include the new task.

40. Pipeline as a Plugin Boundary

The custom-task mechanism effectively provides a lightweight plugin boundary. 

Core Table Pipeline
       |
       +---- Application Task
       |
       +---- Application Task
       |
       v
Extended Table

This allows application-specific transformations without modifying the framework's generic rendering engine.

The most useful way to remember the model is: 

        SPEC
          |

          v
        SPEC
          |
          v
       TASK B
          |

          |

The pipeline is simply the mechanism that moves the specification from one transformation to the next.
