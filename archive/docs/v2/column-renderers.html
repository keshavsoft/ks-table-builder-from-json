1. Purpose

A Column Renderer determines how one column's value should be represented in the Table body. 

Data Row
   |
   v
Column
   |
   v
Column Renderer
   |
   v
Cell Specification
   |

Recursive DOM Builder
   |
   v
DOM
The Column Renderer produces a specification. It does not need to directly create DOM elements.

2. Why Column Renderers Exist

A simple data field can be displayed directly: 

John

But real Tables frequently need richer representations: 

John
$12,450.50
30 Aug 2026
[ Edit ]
[ Delete ]
☑ Selected

A Column Renderer provides the mechanism for converting the raw value into the desired UI specification.

3. Simple Column Without a Renderer

{
    "key": "name",
    "label": "Name"
}

The default behavior can be simple value extraction: 

row[column.key]

resulting in: 

{
    "tagName": "td",
    "textContent": "John"
}

4. Column With a Renderer

{
    "key": "name",

    "label": "Name",

    "render": ({ value }) => {

        return {
            "tagName": "strong",
            "textContent": String(value)
        };

    }
}

The renderer changes the internal representation of the cell.

5. Renderer Input

A useful renderer context can contain: 

{
    value,
    row,
    column,
    rowIndex
}
Value Purpose
value Value associated with the current column.
row Complete data object for the current row.
column Current column definition.
rowIndex Position of the row being rendered.

6. Value

The value is the most common renderer input. 

{
    name: "John",
    age: 30
}

For the age column: 

value === 30

7. Complete Row Context

const row = {
    name: "John",
    age: 30,
    city: "London"
};

A renderer can access the complete row: 

render({
    value,
    row,
    column,
    rowIndex
})

This is useful when the displayed result depends on multiple fields.

8. Simple Text Renderer

render: ({ value }) => {

    return {
        "tagName": "span",
        "textContent": String(value)
    };

}

Result: 

td
 |
 +-- span
       |
       +-- John

9. Formatted Number

{
    "key": "amount",
    "label": "Amount",

    "render": ({ value }) => {

        return {
            "tagName": "span",
            "textContent":
                Number(value).toLocaleString()
        };

    }
}

Raw: 

12450

Display: 

12,450

10. Currency Renderer

render: ({ value }) => {

    return {
        "tagName": "span",
        "textContent":
            "$" +
            Number(value).toFixed(2)
    };

}

Raw: 

12450.5

Display: 

$12450.50

11. Date Renderer

render: ({ value }) => {

    const date =
        new Date(value);

    return {
        "tagName": "span",
        "textContent":
            date.toLocaleDateString()
    };

}

The raw data remains unchanged.

12. Boolean Renderer

render: ({ value }) => {

    return {
        "tagName": "span",

        "textContent":
            value ? "Yes" : "No"
    };

}

This converts a boolean into a human-readable representation.

13. Complex Specification

A renderer is not limited to returning one simple element. 

render: ({ value }) => {

    return {
        "tagName": "div",

        "attributes": {
            "class": "value-wrapper"
        },

        "children": [

            {
                "tagName": "span",
                "textContent": String(value)
            }

        ]
    };

}

14. Nested Renderer Output

td
 |
 +-- div
      |
      +-- span
      |
      +-- button

The renderer can therefore produce arbitrarily complex specification subtrees supported by the generic builder.

15. Action Renderer

{
    "key": "actions",

    "label": "Actions",

    "render": ({ row }) => {

        return {
            "tagName": "button",

            "attributes": {
                "type": "button"
            },

            "textContent": "Edit"
        };

    }
}

16. Row-Aware Rendering

A renderer can use another field in the row. 

{
    id: 15,
    name: "John",
    active: true
}

The action renderer can use id or active to determine what specification to return.

17. Conditional Rendering

render: ({ row }) => {

    if (row.active) {

        return {
            "tagName": "button",
            "textContent": "Disable"
        };

    }

    return {
        "tagName": "button",
        "textContent": "Enable"
    };

}

The decision happens while producing the specification.

18. Checkbox Renderer

{
    "key": "selected",

    "label": "",

    "render": ({ value }) => {

        return {
            "tagName": "input",

            "attributes": {
                "type": "checkbox"
            },

            "properties": {
                "checked": Boolean(value)
            }
        };

    }
}

19. Input Renderer

{
    "key": "name",

    "label": "Name",

    "render": ({ value }) => {

        return {
            "tagName": "input",

            "attributes": {
                "type": "text"
            },

            "properties": {
                "value": value ?? ""
            }
        };

    }
}

This provides an editable representation of the value.

20. Renderer and Events

A renderer can produce a specification containing event definitions if the specification contract supports them. 

render: ({ row }) => {

    return {
        "tagName": "button",

        "textContent": "Edit",

        "events": {
            "click": () => {
                console.log(row);
            }
        }
    };

}

The event is eventually materialized by the DOM layer.

21. Renderer Output Is Not DOM

This distinction is fundamental. 

Renderer
   |
   v
{
    tagName: "button",
    textContent: "Edit"
}

This is a JavaScript object describing the desired element.

      |
      v

23. Renderer and Theme

Column renderers should generally describe what the cell is, while the Theme layer can determine presentation classes. 

Column Renderer
       |
       v
Cell Structure
       |
       v
Theme Transformation
       |
       v
Final Classes
       |

24. Avoid Hard-Coding Theme Classes

Instead of making every renderer know every theme: 

render: () => ({
    tagName: "span",
    attributes: {
        class: "dark:text-white ..."
    }
})

the architecture can keep theme decisions in the theme layer where practical.

25. Renderer and Column Metadata

The renderer receives the column definition and can use its metadata. 

render({
    value,
    row,
    column,
    rowIndex
})

This makes renderers reusable across columns with similar behavior.

26. Renderer Factory

Instead of storing only an inline function, a column can refer to a renderer factory. 

createCurrencyRenderer({
    currency: "USD"
})

The resulting function can then be used for multiple columns.

27. Reusable Currency Renderer

const currencyRenderer =
    ({ value }) => {

        return {
            "tagName": "span",

            "textContent":
                "$" +
                Number(value).toFixed(2)
        };

    };

It can then be assigned to any suitable column.

28. Renderer Composition

Rendering can also be composed from smaller functions. 

value
 |
 v
formatValue()
 |
 v
createValueSpec()
 |
 v
cell spec

This prevents large render functions from becoming difficult to maintain.

29. Value Formatter vs Renderer

Formatter Renderer
Usually changes the value representation. Creates a specification subtree.
Often returns a string. Can return a complex object tree.
Example: number formatting. Example: button + icon + text.

30. Example Formatter

const formatAmount = value => {

    return Number(value)
        .toLocaleString();

};

The renderer can then use it: 

render: ({ value }) => {

    return {
        "tagName": "span",
        "textContent":
            formatAmount(value)
    };

}

31. Renderer Returning Null

A renderer may intentionally return no content if the specification contract allows it. 

render: ({ row }) => {

    if (!row.visible) {
        return null;
    }

    return {
        "tagName": "span",
        "textContent": "Visible"
    };

}

The surrounding body-generation layer must define how null results are handled.

32. Renderer Error Handling

Renderer failures should be handled at an appropriate boundary. 

Data
 |
 v
Column Renderer
 |
 +-- success --> Cell Spec
 |
 +-- failure --> Error Strategy

Possible strategies include logging, fallback content, or propagating the error, depending on application requirements.

33. Renderer and Missing Values

Columns should define how missing values are represented. 

{
    "name": "John"
}

For an email column: 

value === undefined

A renderer can produce: 

"—"

34. Missing Value Renderer

render: ({ value }) => {

    return {
        "tagName": "span",

        "textContent":
            value == null
                ? "—"
                : String(value)
    };

}

35. Renderer and Security

Text content should normally be represented using textContent rather than interpreting arbitrary application data as HTML. 

{
    "tagName": "span",
    "textContent": userValue
}

If a renderer deliberately produces HTML-like structure, it should construct that structure through the specification model rather than treating untrusted strings as markup.

36. Renderer and Column Width

A renderer can concentrate on content while column-level configuration controls layout. 

Column
 |
 +-- width
 +-- alignment
 +-- visibility
 |
 +-- renderer

This keeps content generation and layout configuration conceptually separate.

37. Renderer and Alignment

{
    "key": "amount",

    "label": "Amount",

    "align": "right",

    "render": ({ value }) => ({
        "tagName": "span",
        "textContent":
            Number(value).toLocaleString()
    })
}

Alignment can be translated by a separate column/theme transformation.

38. Renderer and Sorting

Sorting generally operates on the underlying value rather than the rendered specification. 

Raw Data
   |
   +---------> Sorting
   |
   v
Renderer
   |
   v
Display Specification

This prevents presentation formatting from accidentally becoming the sorting source.

39. Renderer and Filtering

Similarly, filtering can operate on the data model while the renderer controls how the surviving values appear. 

Data
 |
 +----> Filter
 |
 v
Renderer
 |
 v
Cell Spec

40. Renderer and Row Index

The row index can be used for display logic. 

render: ({ rowIndex, value }) => {

    return {
        "tagName": "span",

        "textContent":
            `${rowIndex + 1}. ${value}`
    };

}

41. Renderer and Serial Numbers

A dedicated serial column may use the row index. 

render: ({ rowIndex }) => {

    return {
        "tagName": "span",
        "textContent":
            String(rowIndex + 1)
    };

}

This avoids requiring the serial value in the original data.

42. Renderer With Multiple Values

A renderer can combine several fields. 

{
    firstName: "John",
    lastName: "Smith"
}
        
render: ({ row }) => {

    return {
        "tagName": "span",

        "textContent":
            `${row.firstName} ${row.lastName}`
    };

}

43. Renderer Producing Multiple Children

render: ({ row }) => {

    return {

        "tagName": "div",

        "children": [

            {
                "tagName": "strong",
                "textContent":
                    row.firstName
            },

            {
                "tagName": "span",
                "textContent":
                    row.lastName
            }

        ]

    };

}

44. Renderer and Conditional Children

render: ({ row }) => {

    const children = [];

    children.push({
        "tagName": "span",
        "textContent": row.name
    });

    if (row.active) {

        children.push({
            "tagName": "span",
            "textContent": "Active"
        });

    }

    return {
        "tagName": "div",
        "children": children
    };

}

45. Renderer and Custom Elements

Because the output is specification-driven, a renderer can produce custom elements when the generic DOM builder supports them. 

{
    "tagName": "ks-status",
    "attributes": {
        "value": "active"
    }
}

48. Renderer Does Not Own the Cell

The renderer produces the content specification. The surrounding body-generation layer can wrap it in the appropriate td.

      |

Whether the renderer itself returns the td or only its content is an implementation decision; the architecture should keep the responsibility explicit.

51. Renderer Reuse

The same renderer can be assigned to multiple columns. 

currencyRenderer
      |
      +---- Amount
      |
      +---- Price
      |
      +---- Total

This avoids duplicating formatting logic.

52. Renderer Factories and Configuration

createCurrencyRenderer({
    currency: "USD",
    minimumFractionDigits: 2
})

The factory can return a renderer configured for those requirements.

53. Example Renderer Factory

const createCurrencyRenderer =
    ({ currency }) => {

        return ({ value }) => {

            return {
                "tagName": "span",
                "textContent":
                    `${currency} ${value}`
            };

        };

    };

54. Renderer Testing

Because renderers return specifications, they can be tested without a browser DOM. 

Input:

{
    value: 100,
    row: {},
    column: {},
    rowIndex: 0
}

Expected:

{
    tagName: "span",
    textContent: "100"
}

Test Checks

58. Renderer Should Remain Focused

A column renderer should primarily answer: 

"Given this row and column,
what should this cell contain?"

It should not become responsible for: 

Theme resolution
Table construction
tbody creation
Pipeline execution
Global state management
Recursive DOM traversal

60. Final Mental Model

                COLUMN
                  |
                  v
          "Here is the value."
                  |
                  v
         COLUMN RENDERER
                  |
                  v
        "Here is how this value
             should appear."
                  |
                  v
          SPECIFICATION TREE
                  |
                  v
          RECURSIVE BUILDER
                  |
                  v
                 DOM

A Column Renderer is a bridge between raw application data and declarative UI structure.

It does not need to know how the complete Table is built, how themes are resolved, or how recursive DOM construction works. Its focused responsibility is to turn the current column/row context into the specification required for that cell.
