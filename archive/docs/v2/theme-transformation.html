1. Purpose

Theme Transformation is the stage that applies a Theme Specification to an existing component specification. 

God Spec
   |
   v
Theme Spec
   |
   v
Theme Transformation
   |
   v
Resolved Spec
   |
   v
DOM
The Theme does not replace the God Spec. It transforms the existing specification by supplying presentation information.

2. The Two Specifications

The architecture separates the component structure from its presentation. 

God Spec
    |
    +-- What elements exist?
    +-- How are they nested?
    +-- What is the structural skeleton?


Theme Spec
    |
    +-- How should those elements look?
    +-- Which classes should they receive?
    +-- What presentation should be applied?

3. Example God Spec

{
    "tagName": "div",

    "attributes": {
        "class": "table-wrapper"
    },

    "children": [
        {
            "tagName": "table",

                "class": "w-full"
            },

This specification describes structure and may already contain baseline classes.

{
    "tagName": "div",

    "attributes": {
        "class": "table-wrapper space-y-3"
    },

        {

            },

5. Positional Tree Mapping

The Theme Spec mirrors the structural tree. 

God Spec                         Theme Spec

div                              div
 |                                |
 +-- table                        +-- table
      |                                |
      +-- thead                      +-- thead
      |                                |
      +-- tbody                      +-- tbody

Corresponding nodes can therefore be transformed recursively.

6. The Recursive Theme Algorithm

applyTheme({
    inSpec,
    inThemeSpec
})

The algorithm examines the current specification node and its corresponding Theme node, applies the Theme attributes, and recursively processes their children.

7. Current Node

The first step is to identify the current component node. 

const localSpec = inSpec;
const localThemeSpec = inThemeSpec;

The function works on one pair of nodes at a time.

8. Input Validation

if (!localSpec || typeof localSpec !== "object") {
    return localSpec;
}

if (!localThemeSpec || typeof localThemeSpec !== "object") {
    return localSpec;
}

This keeps the transformation safe when either side of the mapping is unavailable.

9. Preserve Existing Attributes

The existing specification attributes are copied first. 

const mergedAttributes = {
    ...(localSpec.attributes || {})
};

This means the Theme transformation does not begin by throwing away the existing attributes.

10. Applying the Theme Class

When the Theme node contains a class, the current implementation assigns that class to the corresponding specification node. 

if (
    localThemeSpec.attributes &&
    localThemeSpec.attributes.class
) {
    mergedAttributes.class =
        localThemeSpec.attributes.class;
}

The Theme class therefore becomes the class of the transformed node.

11. Important Behavior: Class Replacement

The current implementation does not concatenate the existing class with the Theme class. 

God Spec:

class = "table-wrapper"


Theme:

class = "table-wrapper space-y-3"


Result:

class = "table-wrapper space-y-3"

The Theme's class replaces the existing class value.

12. Why This Can Be Useful

If the Theme Spec is intended to be the presentation authority, class replacement provides a deterministic result. 

God Spec
    |
    +-- structural information

Theme
    |
    +-- presentation class

Result
    |
    +-- final class

There is no ambiguity about which class should be used.

13. Why Class Merging May Also Be Useful

In other designs, the original class may contain semantic or component-specific classes that should never be removed. 

Original:
"table-wrapper custom-table"

Theme:
"bg-gray-900"

Potential merged result:
"table-wrapper custom-table bg-gray-900"

Whether replacement or concatenation is correct depends on the intended contract of the Theme Spec.

14. Current Contract

With the implementation shown in this project, the practical contract is: 

Theme class
    |
    v
becomes
    |
    v
final class for that node

This makes the Theme JSON effectively define the final presentation class for each corresponding node.

15. Children

After processing the current node, the function obtains the specification children. 

const specChildren =
    Array.isArray(localSpec.children)
        ? localSpec.children
        : [];

The Theme children are obtained in the same way. 

const themeChildren =
    Array.isArray(localThemeSpec.children)
        ? localThemeSpec.children
        : [];

16. Child Mapping

Each specification child is paired with the Theme child at the same index. 

specChildren.map((childSpec, index) => {

    const matchingThemeChild =
        themeChildren[index];

    return applyTheme({
        inSpec: childSpec,
        inThemeSpec:
            matchingThemeChild
    });

});

17. Positional Matching

The current implementation uses array position as the mapping key. 

Spec children:

[0] div
[1] table
[2] footer


Theme children:

[0] div
[1] table
[2] footer

Therefore: 

Spec[0] <-> Theme[0]
Spec[1] <-> Theme[1]
Spec[2] <-> Theme[2]

18. Why Mirroring Matters

Because the mapping is positional, the Theme tree must preserve the relevant structure of the God Spec. 

God Spec
   |
   +-- A
   |
   +-- B
   |
   +-- C


Theme Spec
   |
   +-- A
   |
   +-- B
   |
   +-- C

Reordering the Theme children changes which Theme is applied to which node.

29. Theme Resolver Fallback

if (themeName && themes[themeName]) {
    return themes[themeName];
}

return themes["default"];

Therefore an unrecognized or absent Theme can fall back to the default Theme.

40. Recursive Invariant

At every recursion level, the transformation follows the same rule: 

Current Spec Node
        +
Current Theme Node
        |
        v
Apply Theme
        |
        v
Recursively process children

This is what allows the implementation to handle arbitrarily nested structures without writing separate logic for each element.

41. Missing Theme Child

If a specification has a child but the Theme does not have a corresponding child: 

matchingThemeChild =
    themeChildren[index];

The result is undefined.

The recursive function then returns the original child specification unchanged because the Theme specification is unavailable for that node.

42. Extra Theme Children

If the Theme contains more children than the component specification, those extra Theme nodes are not independently traversed. 

Spec children:
[A, B]

Theme children:
[A, B, C]

Processed:
A <-> A
B <-> B

C is unused

This follows directly from the implementation's traversal of the specification children.

43. Theme Tree Is Not a Second Independent UI

The Theme JSON should not be interpreted as another DOM tree that will be rendered separately. 

God Spec
   |
   +---- structure


Theme Spec
   |
   +---- transformation input

Only the transformed God Spec is eventually materialized.

45. No Need for Theme Logic in the DOM Builder

The DOM builder should not contain: 

if (theme === "dark") ...
if (theme === "light") ...
if (theme === "medium") ...

It should simply receive the final classes from the resolved specification.
