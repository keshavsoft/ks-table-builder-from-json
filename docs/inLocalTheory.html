📘 Developer Guide: Understanding in-* and local-* Naming Conventions

This project enforces a strict naming convention to make code clear, maintainable, and scalable:

  • in-* → External inputs (parameters, props, API data)
  • local-* → Internal state or derived variables

🔑 Why This Matters for Developers

1. Clear Data Flow

Prefixes immediately tell you whether a variable is coming from outside or computed inside.


// Example: Using in-* and local-* conventions

function renderTable(in-data, in-config) {
  let local-rows = normalizeData(in-data);
  let local-theme = applyTheme(in-config.theme);

  // - in-data: external dataset
  // - in-config: external configuration
  // - local-rows: internal transformation
  // - local-theme: derived state
}

2. Easier Debugging

- Check in-* when external data looks wrong (API, props, user input).
- Check local-* when internal logic or transformations misbehave.

3. Scalable Codebases

Prefixes act like lightweight namespaces, preventing collisions and keeping large projects organized.

4. Better Collaboration

New contributors instantly understand variable roles, reducing onboarding friction and speeding up code reviews.

📊 Comparison

Style Developer Experience Risks
Strict (in-*, local-*) Clear data flow, easy debugging, scalable Slightly verbose
Generic (data, config) Short names, familiar Ambiguous, error-prone
No convention Flexible, fast prototyping Chaos in large teams
✅ Developer Takeaway: This convention is not a burden—it’s a safeguard. It ensures clarity in data flow, confidence in debugging, consistency across teams, and scalability for long-term projects.
