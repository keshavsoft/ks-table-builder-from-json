1. Purpose

A Table has two fundamentally different kinds of information: its structural definition and its application data. 

Table Structure
      |
      v
God Spec

Application Data
      |
      v
Row / Cell Transformation
      |
      v
tbody Specification

The purpose of this layer is to transform data into the specification required for the Table body.

Data is transformed into specification first. The specification is transformed into DOM later.

The data layer does not need to directly create tr and td DOM elements.

3. Example Data

[
    {
        "name": "John",
        "age": 30,
        "city": "London"
    },
    {
        "name": "Mary",
        "age": 25,
        "city": "Paris"
    }
]

This is application data, not DOM structure.

4. Column Definition

The column configuration describes how data should be represented in the Table. 

[
    {
        "key": "name",
        "label": "Name"
    },
    {
        "key": "age",
        "label": "Age"
    },
    {
        "key": "city",
        "label": "City"
    }
]

Columns therefore provide the mapping between application data and Table cells.

5. Data + Columns

Data
  +
Columns
  |
  v
Row Specification

For each data object, the column definitions determine which values become cells and in which order.

6. First Row

Given: 

{
    "name": "John",
    "age": 30,
    "city": "London"
}

And: 

[
    { "key": "name" },
    { "key": "age" },
    { "key": "city" }
]

The resulting row specification is conceptually: 

{
    "tagName": "tr",
    "children": [
        {
            "tagName": "td",
            "textContent": "John"
        },
        {
            "tagName": "td",
            "textContent": "30"
        },
        {
            "tagName": "td",
            "textContent": "London"
        }
    ]
}

7. Multiple Rows

Each data object produces one row specification. 

Data
 |
 +-- Row 1
 |
 +-- Row 2
 |
 +-- Row 3

These row specifications become the children of the tbody. 

{
    "tagName": "tbody",
    "children": [
        RowSpec1,
        RowSpec2,
        RowSpec3
    ]
}

9. The Existing God Spec

The structural Table specification can contain an empty body: 

{
    "tagName": "tbody",
    "attributes": {
        "slot": "body"
    },
    "children": []
}

The data transformation populates that part of the specification. 

Empty tbody
    |
    v
Data Transformation
    |
    v
tbody with row specifications

10. Why Keep tbody in the God Spec?

The God Spec describes the structural skeleton. 

table
 |
 +-- thead
 |
 +-- tbody
 |
 +-- tfoot

Data processing should not need to create the entire Table structure.

It only needs to supply the dynamic body content.

11. Row Factory

A row can be produced by a dedicated function. 

createRowSpec({
    inRow,
    inColumns
})

Its responsibility is to transform one data object into one tr specification.

12. Cell Factory

A row factory can delegate individual cell creation. 

createCellSpec({
    inValue,
    inColumn
})

The cell factory converts a value and its column definition into a cell specification.

13. Row → Cell Mapping

Row
 |
 +-- Column 1 -> Cell 1
 |
 +-- Column 2 -> Cell 2
 |
 +-- Column 3 -> Cell 3
 |
 +-- Column 4 -> Cell 4

This mapping guarantees that the body follows the same column order defined for the Table.

14. Header and Body Must Agree

If the header contains: 

Name | Age | City

the body should produce: 

John | 30 | London
Mary | 25 | Paris

Therefore the same column definition is an important source of truth for both header and body generation.

15. Column as the Mapping Contract

Column Definition
       |
       +-- key
       +-- label
       +-- renderer
       +-- attributes
       +-- options
       |
       v
Header + Body

The column definition can describe both how the column is presented and how its values are obtained.

16. Simple Value Extraction

For a simple column: 

{
    "key": "name"
}

the corresponding value can be obtained from: 

row[column.key]

For the row: 

{
    "name": "John"
}

the value is: 

"John"

17. Nested Data

Applications may contain nested objects. 

{
    "customer": {
        "name": "John"
    }
}

A column can use a suitable value-access strategy rather than forcing the generic Table renderer to understand the data model.

18. Value Transformation

A column may need to transform a raw value before creating its cell specification.

    |
    v

    |
    v

    |
    v

For example, a numeric value could be converted to a formatted string.

19. Custom Cell Rendering

A column can also produce more than plain text. 

Column
  |
  v

  |
  v

The cell could contain: 

span
button
input
link
icon
custom element

The resulting structure remains a specification tree.

20. Example: Button Cell

{
    "tagName": "td",
    "children": [
        {
            "tagName": "button",
            "attributes": {
                "type": "button"
            },
            "textContent": "Edit"
        }
    ]
}

The body-generation layer creates this specification. The DOM builder later materializes it.

21. Example: Input Cell

{
    "tagName": "td",
    "children": [
        {
            "tagName": "input",
            "attributes": {
                "type": "text"
            }
        }
    ]
}

Again, the data-to-body layer does not need to directly create the DOM element.

22. Empty Data

If there is no data: 

[]

the body can simply remain: 

{
    "tagName": "tbody",
    "children": []
}

Empty-state behavior can be introduced separately if required.

23. Empty-State Row

An optional empty-state transformation can produce: 

{
    "tagName": "tr",
    "children": [
        {
            "tagName": "td",
            "attributes": {
                "colspan": "3"
            },
            "textContent": "No data"
        }
    ]
}

This remains a normal specification transformation.

27. Serial Column

If a serial column is enabled, the row transformation can prepend an additional cell. 

Data Row
   |
   v

   +
Data Cells
   |
   v

For example: 

1 | John | 30 | London
2 | Mary | 25 | Paris

28. Serial Number Is UI Data

The serial number does not necessarily have to exist in the original application object. 

Application Object
{
    "name": "John",
    "age": 30
}

can become: 

Row
{
    serial: 1,
    name: "John",
    age: 30
}

or the serial value can be injected directly into the generated cell specification.

29. Body Generation as a Middleware

The data-to-body operation fits naturally into the pipeline model. 

God Spec
    |
    v
Theme
    |
    v
Header
    |
    v
Body/Data Task
    |
    v
Footer
    |
    v
Serial / Other Tasks
    |
    v
Resolved Spec

The task modifies the specification and passes it to the next stage.

30. Middleware Contract

const createBodyTask = ({
    inData,
    inColumns
}) => {

    return ({ inSpec }) => {

        // Generate body specification.

        return inSpec;
    };
};

The factory captures the configuration while the returned function participates in the generic pipeline.

31. Body Task Input

{
    inData,
    inColumns,
    inSpec
}

The important distinction is: 

inData
    |
    +-- application information

inColumns
    |
    +-- display/mapping information

inSpec
    |
    +-- Table structure

32. Body Task Output

The result is still the complete Table specification. 

inSpec
   |
   v
Body Transformation
   |
   v
updated Table Spec

This is important because the next middleware does not need a separate object type.

The pipeline therefore has a simple and consistent contract.

34. Body Task Should Not Build DOM

The body task should not do: 

document.createElement("tbody")
document.createElement("tr")
document.createElement("td")

Instead it creates specification objects. 

{
    "tagName": "tr",
    "children": [...]
}

35. Why This Matters

Once data generation is separated from DOM creation, the same data transformation can be inspected, tested, logged, or transformed further before rendering. 

Data
 |
 v
Spec
 |
 +-- inspect
 +-- transform
 +-- theme
 +-- validate
 |
 v
DOM

36. Body Specification Is Declarative

A generated row does not say: 

"Create a tr now."

It says: 

{
    "tagName": "tr",
    "children": [...]
}

The actual creation happens later.

const data = [
    {

    {
        key: "name"

    {

    }

39. Dynamic Body Does Not Require a Second God Spec

The original Table God Spec can remain the structural source. 

God Spec
   |
   +-- wrapper
   +-- toolbar
   +-- table
        |
        +-- thead
        +-- tbody
        |
        +-- footer

The body task fills the dynamic portion.

40. Data Transformation and Theme Transformation

Both are specification transformations, but they solve different problems.

Transformation Concern
Theme Presentation/classes.
Column Column structure.
Body/Data Dynamic rows and cells.
Header Header structure.
Footer Footer structure.

41. Order of Transformations

The exact order depends on the component implementation, but dependencies should determine ordering. 

Columns
   |
   v
Header / Body
   |
   v
Theme / Other Presentation
   |
   v
Resolved Spec

If one task requires the output of another task, the dependency must be reflected in the pipeline order.

42. Row Renderer

A row renderer can be treated as a specification factory. 

createRowSpec(row, columns)
        |
        v
{
    tagName: "tr",
    children: [...]
}

This makes row generation independent from DOM creation.

43. Cell Renderer

A cell renderer can similarly produce a specification. 

createCellSpec(value, column)
        |
        v
{
    tagName: "td",
    children: [...]
}

The cell can therefore contain any supported specification structure.

44. Custom Column Renderer

{
    "key": "actions",

    "render": ({ row }) => {

        return {
            "tagName": "button",
            "textContent": "Edit"
        };

    }
}

The renderer can return a specification rather than directly manipulating the DOM.

45. Body as a Tree Generator

Data
 |
 +-- object
 |    |
 |    +-- column
 |         |
 |         +-- cell spec
 |
 +-- object
 |    |
 |    +-- column
 |         |
 |         +-- cell spec
 |
 +-- object
      |
      +-- column
           |
           +-- cell spec

The final result is a specification subtree.

46. Body Generation Does Not Care About DOM Depth

A cell can be simple: 

td
 |
 +-- text

or complex: 

td
 |
 +-- div
      |
      +-- button
      |
      +-- button
      |
      +-- span

Both are valid specification subtrees.

47. Complex Cell Example

{
    "tagName": "td",

    "children": [
        {
            "tagName": "div",

            "attributes": {
                "class": "actions"
            },

            "children": [
                {
                    "tagName": "button",
                    "textContent": "Edit"
                },
                {
                    "tagName": "button",
                    "textContent": "Delete"
                }
            ]
        }
    ]
}

The recursive builder can handle the entire subtree without special Table logic.

56. Final Mental Model

               GOD SPEC
                   |
                   |
          "This is the skeleton."
                   |
                   v
          +----------------+
          |   PIPELINE     |
          |----------------|
          | Theme          |
          | Columns        |
          | Data / Body    |
          | Header         |
          | Footer         |
          | Custom         |
          +----------------+

           is fully resolved."

                   |

                   |
                   v

Data-to-tbody is therefore not a separate DOM-rendering mechanism. It is a specification transformation that converts application data into the body subtree of the existing Table specification.

The God Spec remains the structural skeleton, the pipeline fills and transforms that skeleton, and the recursive DOM builder finally materializes the resulting tree.
