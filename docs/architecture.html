1. Architectural Overview

The project is based on a JSON-driven rendering model. Instead of directly constructing the complete DOM tree inside the component renderer, the UI is first described as a declarative specification.

This separation is the central architectural decision of the project.

2. The Four Major Stages

The complete rendering process can be understood as four stages.

Stage 1 — Description

3. JSON World vs DOM World

One of the most important boundaries in the project is the separation between specification objects and browser DOM objects. 

              JSON WORLD
                  |
                  |
        specification changes
                  |
                  v
          Resolved JSON Spec
                  |
                  |
          materialization
                  |
                  v
               DOM WORLD

Theme application belongs to the JSON world. Header and footer transformations belong to the JSON world. Column transformations belong to the JSON world.

DOM creation should happen only after these decisions have been resolved.

The God Spec is the structural blueprint of the component.

It does not directly create DOM elements. It is data describing the elements.

The runner does not need to know anything about Tables.

16. Recursive DOM Builder

buildSpecElement() is the bridge between the JSON specification and actual DOM. 

Specification

      +---- Node?

      +---- Object?

              |

Because the input is a tree, recursion is a natural fit.

18. Why the DOM Builder Is Generic

The same specification engine can create:

table
thead
tbody
tfoot
form
label
input
button
section

There is no need to create separate DOM builders for each component.

     |

24. Final Architectural Rule

The framework describes the UI, transforms the description, and only then creates the DOM.

This separation is what allows the Table architecture to become a reusable UI rendering foundation rather than a collection of Table-specific DOM creation routines.
