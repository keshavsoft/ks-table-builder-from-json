Columns and Header

How column definitions drive both the Table header and body
Documentation Home Architecture God Spec Themes Pipeline Tasks Recursive Builder Element Builder Table Renderer Data to Tbody

1. Purpose

Columns describe how a Table represents data. They form the contract between the application's data and the visual Table. 

Application Data
       |
       v
Column Definitions
       |
       +----------------+
       |                |
       v                v
    Header             Body
       |                |
       v                v
      th               td
A column is more than a header label. It can define how values are obtained, displayed, transformed, and rendered.

2. The Basic Column

The simplest column can contain a data key and a display label. 

{
    "key": "name",
    "label": "Name"
}

The key identifies the data field. The label identifies the header text.

3. Multiple Columns

[
    {
        "key": "name",
        "label": "Name"
    },

    {
        "key": "age",
        "label": "Age"
    },

    {
        "key": "city",
        "label": "City"
    }
]

The order of this array normally determines the visual order of the columns.

4. Column Order

Given: 

[
    { "key": "name" },
    { "key": "age" },
    { "key": "city" }
]

the Table follows: 

Name | Age | City

If the definitions are reordered: 

[
    { "key": "city" },
    { "key": "name" },
    { "key": "age" }
]

the Table can correspondingly become: 

City | Name | Age

5. Header Generation

The column definitions can be transformed into th specifications. 

Column
    |
    v
Header Cell Spec
    |
    v
th

For example: 

{
    "key": "name",
    "label": "Name"
}

can produce: 

{
    "tagName": "th",
    "textContent": "Name"
}

6. Complete Header

{
    "tagName": "thead",

    "children": [
        {
            "tagName": "tr",

            "children": [
                {
                    "tagName": "th",
                    "textContent": "Name"
                },
                {
                    "tagName": "th",
                    "textContent": "Age"
                },
                {
                    "tagName": "th",
                    "textContent": "City"
                }
            ]
        }
    ]
}

7. Body Generation

The same column definitions can be used to generate body cells. 

Column
    |
    +-- key
    |
    v
row[key]
    |
    v
Cell Value
    |
    v
td Spec

8. Header and Body Share One Column Definition

                 COLUMNS
                    |
          +---------+---------+
          |                   |
          v                   v
       HEADER               BODY
          |                   |
          v                   v
         th                  td

This prevents the header and body from independently deciding their column order.

9. Why This Is Important

Without a shared column definition, it is possible for the header and body to become inconsistent. 

Header:
Name | Age | City

Body:
Name | City | Age

A common column contract avoids this mismatch.

10. Column as a Mapping Contract

Column
 |
 +-- identifies data
 |
 +-- identifies display label
 |
 +-- determines position
 |
 +-- determines rendering
 |
 +-- may determine styling
 |
 +-- may determine behavior

This makes the column definition one of the most important declarative structures in a data-driven Table.

11. Simple Data Mapping

const row = {
    name: "John",
    age: 30,
    city: "London"
};
        
const column = {
    key: "name",
    label: "Name"
};

The value is: 

row[column.key]

Result: 

"John"

12. Creating a Cell

{
    "tagName": "td",
    "textContent": "John"
}

This specification can later be passed through the generic DOM builder.

13. Column Renderer

A column can optionally provide a rendering strategy. 

{
    "key": "amount",
    "label": "Amount",

    "render": ({ value }) => {

        return {
            "tagName": "span",
            "textContent": String(value)
        };

    }
}

The renderer returns a specification rather than directly manipulating the DOM.

14. Why Renderers Return Specifications

      |

This preserves the specification-first architecture.

15. Text Cell vs Complex Cell

A simple column can produce: 

td
 |
 +-- text

A complex column can produce: 

td
 |
 +-- div
      |
      +-- span
      |
      +-- button
      |
      +-- button

Both are just specification trees.

16. Column Attributes

A column can potentially carry presentation information. 

{
    "key": "name",
    "label": "Name",

    "attributes": {
        "class": "customer-name"
    }
}

Such information can be incorporated into the generated specification.

17. Header Attributes

Header-specific information can be transformed into the th specification. 

{
    "key": "name",
    "label": "Name",

    "headerAttributes": {
        "class": "text-left"
    }
}

Conceptually: 

{
    "tagName": "th",

    "attributes": {
        "class": "text-left"
    },

    "textContent": "Name"
}

18. Body Attributes

A column may also specify attributes for its body cells. 

{
    "key": "amount",

    "cellAttributes": {
        "class": "text-right"
    }
}

This can be transformed into the corresponding td specification.

19. Keeping Header and Cell Concerns Separate

Column
 |
 +-- key
 +-- label
 +-- headerAttributes
 +-- cellAttributes
 +-- renderer

This lets one column definition describe both sides of the Table without forcing identical configuration on th and td.

20. Column Visibility

A column may need to be conditionally visible. 

{
    "key": "internalId",
    "label": "Internal ID",
    "visible": false
}

A column transformation can remove or ignore this column before header and body specifications are produced.

22. Serial Column

A serial column can be represented as an additional column or introduced by a dedicated Table task. 

[
    Serial,
    Name,
    Age,
    City
]

The same effective column ordering can then drive both header and body generation.

23. Serial Header

{
    "tagName": "th",
    "textContent": "#"
}

The serial column therefore has a header representation just like any other column.

24. Serial Body Cell

{
    "tagName": "td",
    "textContent": "1"
}

The value is derived from the row position rather than the application's data object.

25. Nested Data

Real-world data may contain nested structures. 

{
    "customer": {
        "name": "John"
    }
}

A column can provide a value-access strategy appropriate for the application's data shape. 

customer.name

The result can still become a normal cell specification.

26. Value Formatting

Raw data and display data do not always have the same form. 

Raw:
123456.78

Display:
123,456.78

The column's transformation or renderer can perform this presentation conversion.

27. Date Formatting

Raw:
2026-08-30T12:30:00

Display:
30 Aug 2026

The underlying data remains unchanged while the column controls its displayed representation.

28. Boolean Rendering

A boolean value can be represented as text: 

true -> "Yes"
false -> "No"

or as a richer specification: 

td
 |
 +-- span
      |
      +-- "Yes"

29. Action Column

An action column often has no direct data key. 

{
    "key": "actions",
    "label": "Actions"
}

Its renderer can construct controls based on the current row. 

Row
 |
 v
Action Column
 |
 v
Button Specification

30. Action Column Example

{
    "key": "actions",

    "label": "Actions",

    "render": ({ row }) => {

        return {
            "tagName": "button",

            "attributes": {
                "type": "button"
            },

            "textContent": "Edit"
        };

    }
}

31. Checkbox Column

A checkbox column can similarly produce a nested specification. 

{
    "key": "selected",

    "label": "",

    "render": ({ value }) => {

        return {
            "tagName": "input",

            "attributes": {
                "type": "checkbox"
            },

            "properties": {
                "checked": value
            }
        };

    }
}

32. Input Column

Editable cells can be represented in the same manner. 

td
 |
 +-- input

The data-to-body transformation produces the specification; the generic builder materializes it.

33. Column Renderer Receives Row Context

A renderer may need more than the current value. 

render({
    value,
    row,
    column,
    rowIndex
})

This enables row-dependent rendering while keeping the output declarative.

34. Row Index

The row index can be used for: 

Serial numbers
Alternating content
Conditional actions
Row-specific controls

It is particularly useful when generating UI-only columns.

41. Column Model

A normalized internal model might conceptually contain: 

{
    key,
    label,
    visible,
    headerAttributes,
    cellAttributes,
    render
}

The actual project model can contain whatever fields its requirements need.

42. Columns Do Not Need to Know DOM Recursion

A column renderer can return a nested specification without knowing how deep the eventual DOM tree will be.

Theme handling remains a separate concern.

The key point is that column logic and theme lookup remain conceptually separate.

44. Columns and Classes

A column can describe semantic presentation requirements while the theme layer supplies theme-specific classes.

45. Example Theme Interaction

Column:
{
    "key": "name",
    "label": "Name"
}

The generated cell may initially be: 

{
    "tagName": "td"
}

The theme transformation can then apply the appropriate class according to the corresponding Theme Spec.

46. Column Width

A column can also carry layout information where required. 

{
    "key": "name",
    "label": "Name",
    "width": "30%"
}

The column transformation can translate this requirement into the appropriate specification representation.

47. Alignment

{
    "key": "amount",
    "label": "Amount",
    "align": "right"
}

Alignment can become a cell/header attribute or class during specification transformation.

48. Sorting Metadata

A column may also carry metadata used by sorting behavior. 

{
    "key": "name",
    "label": "Name",
    "sortable": true
}

The sorting system can use this metadata without requiring the generic DOM builder to understand sorting.

49. Filtering Metadata

{
    "key": "city",
    "label": "City",
    "filterable": true
}

Again, this is Table behavior rather than generic DOM behavior.

51. Complete Example

const columns = [

    {
        key: "name",
        label: "Name"
    },

    {
        key: "age",
        label: "Age"
    },

    {
        key: "city",
        label: "City"
    },

    {
        key: "actions",
        label: "Actions",

        render: ({ row }) => {

            return {
                tagName: "button",
                attributes: {
                    type: "button"
                },
                textContent: "Edit"
            };

        }
    }

];

52. Resulting Header

Name | Age | City | Actions

The action column has no need for a corresponding property in the data object.

53. Resulting Body

John | 30 | London | Edit
Mary | 25 | Paris  | Edit

The first three columns read values from the row. The final column generates its content through its renderer.

54. Header and Body as Two Projections

A useful mental model is that the same column model is projected into two different structures. 

                 COLUMN MODEL
                       |
             +---------+---------+
             |                   |
             v                   v
       HEADER PROJECTION    BODY PROJECTION
             |                   |
             v                   v
            th                  td

This keeps the Table model coherent.

55. Column Changes Propagate Naturally

If a column is added: 

Columns
   |
   +-- Name
   +-- Age
   +-- City
   +-- Country

both header and body generation can automatically account for the new column.

56. Column Removal

Removing a column from the resolved column set removes its corresponding header and body representation. 

Before:
Name | Age | City

After:
Name | City

57. Column Reordering

Reordering the resolved column list changes the presentation order consistently. 

Before:
Name | Age | City

After:
City | Name | Age

The body follows the same order because it uses the same resolved columns.

Columns are the bridge between data and Table structure.

The God Spec provides the structural skeleton, column transformations determine what the Table's columns mean, data transformations generate the body, and the recursive DOM builder finally materializes the resulting specification.
