The low-level layer responsible for materializing one specification node

1. Purpose

The DOM Element Builder is the low-level rendering layer that converts an individual JSON specification node into an actual DOM element. 

Specification Node
        |
        v
DOM Element Builder
        |
        v
DOM Element

The recursive DOM builder understands the tree. The DOM Element Builder handles the individual element.

3. One Node vs Entire Tree

Layer Responsibility
Recursive DOM Builder Understands the hierarchy and recursively processes children.
DOM Element Builder Creates/configures the DOM representation of an individual specification node.

4. Basic Input

A specification node may look like: 

{
    "tagName": "div",
    "attributes": {
        "class": "table-wrapper"
    }
}

The DOM Element Builder converts this into the corresponding browser element. 

<div class="table-wrapper"></div>

5. tagName

The tagName identifies the type of DOM element to create. 

{
    "tagName": "button"
}

Conceptually: 

document.createElement("button")

The builder should use the specification rather than hard-code individual HTML element types.

6. Attributes

Attributes are represented by the specification's attributes object. 

{
    "tagName": "input",
    "attributes": {
        "type": "text",
        "name": "search",
        "placeholder": "Search"
    }
}

The builder translates these into actual HTML attributes. 

<input
    type="text"
    name="search"
    placeholder="Search"
>

7. Classes

Classes are normally represented through the class attribute. 

{
    "tagName": "div",
    "attributes": {
        "class": "table-wrapper space-y-3"
    }
}

By the time the specification reaches this layer, theme transformations may already have supplied the desired classes. 

Theme
  |
  v
class information
  |
  v
Resolved Spec
  |
  v
DOM Element Builder

8. Theme Responsibility Ends Before This Layer

The DOM Element Builder should not resolve theme names.

It should not contain logic such as: 

if (theme === "dark") {
    element.classList.add(...);
}

Instead: 

Theme Name
    |
    v
Theme Resolver
    |
    v
Theme Spec
    |
    v
Theme Transformation
    |
    v
Resolved Spec
    |
    v
DOM Element Builder

9. Properties

A specification can distinguish DOM properties from HTML attributes. 

{
    "tagName": "input",
    "properties": {
        "value": "Keshav",
        "disabled": false
    }
}

These values can be applied directly to the DOM element as JavaScript properties. 

element.value = "Keshav";
element.disabled = false;

10. Attribute vs Property

Specification Meaning
attributes HTML attributes.
properties JavaScript DOM properties. 
{
    "attributes": {
        "type": "text"
    },

    "properties": {
        "value": "Hello"
    }
}

11. Text Content

Text can be represented declaratively. 

{
    "tagName": "span",
    "textContent": "Hello World"
}

The resulting element contains: 

<span>Hello World</span>

12. Events

If the specification supports event definitions, the DOM Element Builder can translate those definitions into event listeners. 

{
    "tagName": "button",
    "textContent": "Save",
    "events": {
        "click": handleSave
    }
}

Conceptually: 

element.addEventListener(
    "click",
    handleSave
);

The important architectural point is that the event definition arrives through the specification rather than being hard-coded into the generic element creation process.

15. Example: Table

Consider a small Table specification: 

{
    "tagName": "table",
    "attributes": {
        "class": "w-full"
    },
    "children": [
        {
            "tagName": "thead"
        },
        {
            "tagName": "tbody"
        }
    ]

The recursive builder visits: 

table
 |
 +-- thead

 +-- tbody

Each node eventually passes through the element builder.

20. The Element Builder Should Be Generic

The element builder should not know whether an element belongs to a Table, Form, Card, Toolbar, or another component. 

Table
Form
Card
Dialog
Toolbar
List
     |
     v
Generic DOM Element Builder

Its input is the specification node, not the business meaning of the component.

21. No Table Logic

The generic element builder should not contain logic such as: 

if (tagName === "table") {
    // Table-specific behavior
}

if (isSerialColumn) {
    // Serial-specific behavior
}

Such behavior belongs in the Table's specification transformations.

22. No Form Logic

Likewise, it should not contain: 

if (isFormField) {
    // Form-specific behavior
}

A Form transformation should produce the correct specification. The generic builder then materializes it.

23. No Theme Resolution

Theme resolution belongs upstream.

    |

24. The Builder Receives Final Decisions

By the time a specification node reaches the DOM Element Builder, decisions such as the following should already have been made:

  • which node exists
  • which classes it has
  • which attributes it has
  • which properties it has
  • what text it contains
  • which event definitions apply

The builder's job is to materialize those decisions.

26. Conceptual Implementation

const domElementBuilder = ({ inSpec }) => {

    if (
        !inSpec ||
        typeof inSpec !== "object" ||
        !inSpec.tagName
    ) {
        return null;
    }

    const element =
        document.createElement(
            inSpec.tagName
        );

    // Apply attributes.

    // Apply properties.

    // Apply text.

    // Apply events.

    return element;
};

The actual implementation may contain additional behavior, validation, normalization, or helper functions.

27. Attribute Application

A generic attribute loop can conceptually look like: 

Object.entries(
    inSpec.attributes || {}
).forEach(([name, value]) => {

    element.setAttribute(
        name,
        value
    );

});

The real implementation may need special handling for boolean attributes or other cases.

28. Property Application

Object.entries(
    inSpec.properties || {}
).forEach(([name, value]) => {

    element[name] = value;

});

This is different from setAttribute().

29. Event Application

Object.entries(
    inSpec.events || {}
).forEach(([eventName, handler]) => {

    if (typeof handler === "function") {

        element.addEventListener(
            eventName,
            handler
        );

    }

});

Event handling remains declarative at the specification level, while actual listener registration occurs during materialization.

30. Text Application

if (
    typeof inSpec.textContent === "string"
) {
    element.textContent =
        inSpec.textContent;
}

The exact rules can be expanded if the specification supports additional content types.

31. Why the Builder Should Be Small

The element builder sits at the foundation of the DOM layer. If it starts containing component-specific rules, every component becomes coupled to the same implementation. 

Generic Builder
       |
       +-- Table rules
       +-- Form rules
       +-- Card rules
       +-- Dialog rules
       +-- Theme rules
       +-- Data rules

This is precisely the coupling the architecture is intended to avoid.

33. Testing

The DOM Element Builder can be tested independently with small specification nodes. 

Input:
{
    "tagName": "div",
    "attributes": {
        "class": "box"
    }
}

Expected:
div.box

More complete tests can verify properties, attributes, text, events, and other supported specification features.

The DOM Element Builder should be deliberately boring.

The intelligence belongs in the specification and its transformation pipeline. The element builder's job is to faithfully materialize that final specification into a DOM element.
