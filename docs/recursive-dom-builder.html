1. Purpose

The recursive DOM builder is the final stage that converts the resolved JSON specification into actual browser DOM elements. 

God Spec
    |
    v
Transformation Pipeline
    |
    v
Resolved JSON Spec
    |
    v
Recursive DOM Builder
    |
    v
DOM
The recursive builder does not decide what the UI should be. It materializes what the specification says.

2. Why Recursion?

The specification itself is a tree. 

div
 |
 +-- div
 |    |
 |    +-- span
 |
 +-- table
      |
      +-- thead
      |    |
      |    +-- tr
      |         |
      |         +-- th
      |
      +-- tbody

Since every node can contain more children, the same operation can be applied repeatedly to every level of the tree.

3. Specification Tree

A specification can be viewed as a recursive structure: 

Spec
 |
 +-- tagName
 |
 +-- attributes
 |
 +-- properties
 |
 +-- textContent
 |
 +-- children
       |
       +-- Spec
       +-- Spec
       +-- Spec

The children property is what creates the recursive relationship.

4. Basic Algorithm

buildSpecElement(spec):

    if spec is invalid:
        return nothing

    create current DOM element

    apply current specification

    for every child:
        recursively build child

        append child

    return current DOM element

This algorithm works regardless of how deeply nested the specification becomes.

5. Simple Example

{
    "tagName": "div",
    "children": [
        {
            "tagName": "span",
            "textContent": "Hello"
        }
    ]
}

The builder first creates the div. Then it recursively processes the span. 

div
 |
 +-- span

Consider a deeply nested structure:

      |
      +-- div
           |
           +-- form
                |

8. The Current Node

Every recursive invocation operates on one current specification node. 

inSpec
  |
  v
current node

The builder first handles that node and then processes its children.

9. Creating the Current Element

Once the node is validated, the builder can create the corresponding DOM element. 

const element = document.createElement(
    inSpec.tagName
);

The exact DOM creation logic can be delegated to domElementBuilder().

10. Applying Attributes

If the specification contains attributes, those attributes are applied to the newly created element. 

{
    "tagName": "div",
    "attributes": {
        "class": "table-wrapper",
        "id": "orders"
    }
}

Conceptually: 

div
 |
 +-- class="table-wrapper"
 +-- id="orders"

11. Applying Properties

Properties can be applied separately from HTML attributes. 

{
    "tagName": "input",
    "properties": {
        "value": "Keshav"
    }
}

The resulting DOM element receives the corresponding JavaScript property.

12. Applying Text

{
    "tagName": "span",
    "textContent": "Hello"
}

The element receives its text content before it is returned to its parent. 

span
 |
 +-- "Hello"

13. Processing Children

Children are processed after the current node has been established. 

const children = Array.isArray(inSpec.children)
    ? inSpec.children
    : [];

children.forEach(childSpec => {

    const childElement =
        buildSpecElement(childSpec);

    // append child

});

Each child invokes the same builder again.

16. Recursive Processing Order

The builder generally follows this sequence: 

1. Validate specification
2. Create current element
3. Apply attributes
4. Apply properties
5. Apply text
6. Process children recursively
7. Append children
8. Return current element

The exact internal ordering can vary according to the project's DOM builder implementation, but the important concept is that child specifications are recursively materialized.

17. Recursion Terminates at Leaf Nodes

A leaf node has no children. 

{
    "tagName": "span",
    "textContent": "Hello",
    "children": []
}

The recursive process stops at this node. 

span
 |
 +-- "Hello"

No children
    |
    v
Return

18. Empty Children

A specification may omit children or provide an empty array. 

{
    "tagName": "div"
}

Conceptually this is equivalent to: 

{
    "tagName": "div",
    "children": []
}

The builder can therefore normalize missing children to an empty array.

19. Invalid Children

A robust recursive builder should not assume every child is valid. 

children
   |
   +-- valid Spec
   |
   +-- null
   |
   +-- invalid value
   |
   +-- valid Spec

Invalid entries can be ignored or handled according to the component's validation rules.

25. Important Architectural Boundary

Once the specification reaches the recursive DOM builder, structural decisions should already have been resolved.

The builder's responsibility is primarily materialization.

26. Builder Does Not Decide Header Visibility

The builder should not contain logic such as: 

if (showHeader) {
    create thead
}

Instead, the Header Task should have already transformed the specification.

33. Recursive Builder Pseudocode

function buildSpecElement({ inSpec }) {

    if (!inSpec || typeof inSpec !== "object") {
        return null;
    }

    const element =
        domElementBuilder({
            inSpec
        });

    const children =
        Array.isArray(inSpec.children)
            ? inSpec.children
            : [];

    children.forEach(childSpec => {

        const childElement =
            buildSpecElement({
                inSpec: childSpec
            });

        if (childElement) {
            element.appendChild(childElement);
        }

    });

    return element;
}

This illustrates the central recursive pattern.

34. Complexity

If the specification contains N nodes, the builder generally visits each node once. 

Node 1
  |
Node 2
  |
Node 3
  |
...
  |
Node N

The fundamental traversal is therefore proportional to the number of nodes in the specification.

35. Deep Trees

A deeply nested specification naturally produces deeper recursion. 

Level 1
  |
  +-- Level 2
       |
       +-- Level 3
            |
            +-- Level 4
                 |
                 +-- Level 5

Normal UI trees are generally well suited to this recursive representation.

36. Specification Validation

Before creating an element, the builder can validate the basic specification shape. 

if (!inSpec) return null;

if (typeof inSpec !== "object") {
    return null;
}

More detailed validation can be introduced separately if the framework requires it.

37. Why Not Hard-Code the Table?

Without a specification-driven builder, the Table renderer could become filled with direct DOM operations. 

create div
create table
create thead
create tr
create th
create tbody
create tr
create td
...

The specification model moves those structural details into data and leaves the builder generic.

              SPECIFICATION TREE

The recursive DOM builder is intentionally simple: it walks the specification tree and materializes that tree as DOM.

The intelligence about themes, columns, visibility, dynamic UI, and other component behavior should happen before this stage through specification transformations.
