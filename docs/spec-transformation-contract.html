1. Purpose

This document defines the conceptual contract between the different transformation stages used to build a component from JSON specification. 

Input Specification
        |
        v
Transformation
        |
        v
Output Specification
The specification is the common language shared by the transformation stages.

2. The Central Contract

A transformation receives a specification and produces a specification. 

Spec
 |
 v
transform()
 |
 v
Spec

The next transformation can therefore consume the result without needing to know how the previous transformation implemented its work.

3. Basic Function Shape

const transform = ({
    inSpec
}) => {

    // transform specification

    return inSpec;
};

This is the simplest representation of the contract.

4. Input and Output

Part Meaning
inSpec The current specification entering the stage.
return value The specification passed to the next stage.

5. The Specification Model

A specification node generally describes an element and its properties. 

{
    "tagName": "div",

    "attributes": {
        "class": "example"
    },

    "children": []
}

Nested nodes form the complete specification tree.

6. Specification Tree

div

A transformation operates on this tree rather than directly on the browser DOM.

The God Spec is the initial specification tree from which the component is assembled.

8. Transformation Does Not Mean Complete Reconstruction

A transformation does not necessarily rebuild the complete specification. 

Original Spec
 |
 +-- toolbar       unchanged
 |
 +-- table
      |
      +-- thead    unchanged
      |
      +-- tbody    modified

A transformation may change only the portion for which it is responsible.

11. Target Identification

A transformation needs a reliable way to identify the subtree it owns. 

{
    "tagName": "tbody",

    "attributes": {
        "slot": "body"
    }
}

Here slot="body" can act as an explicit contract identifying the dynamic body region.

12. Structural Contract

A transformation should know what part of the specification it is responsible for. 

Data Task

    +-- owns tbody content


Header Task

13. Responsibility Boundaries

Transformation Primary Responsibility
Column Resolve column definitions.
Header Create header structure.
Data Create body rows.
Renderer Create cell content.
Theme Apply presentation information.

14. Do Not Cross Responsibilities Unnecessarily

A Data Transformation should not need to contain Theme selection logic. 

Data Task

    rows
    columns
    cells

        NOT

    dark theme
    light theme
    medium theme

Theme behavior belongs to the Theme layer.

15. Specification Preservation

A transformation should preserve information that belongs to other parts of the specification unless it intentionally owns that information. 

Before:

{
    tagName: "table",

    attributes: {
        class: "table"
    },

    children: [...]
}

A Data Task should not accidentally remove the existing attributes.

16. Preserve Unrelated Properties

const tableSpec = {
    tagName: "table",

    attributes: {
        class: "table"
    },

    children: [...]
};

If a transformation only needs to modify children, it should preserve the other properties. 

tableSpec.children = newChildren;

return tableSpec;

17. Transformation as a Local Operation

18. Mutation Contract

One implementation style is to mutate the incoming specification.

    inSpec
}) => {

    inSpec.children = newChildren;

    return inSpec;
};

The same object continues through the pipeline.

42. Transformations Can Be Recursive

A transformation may recursively traverse the specification tree. 

transform(node)
    |
    +-- transform node
    |
    +-- transform children

This is especially useful for Theme processing.

43. Recursive Transformation

div
 |
 +-- table
      |
      +-- thead
      |    |
      |    +-- tr
      |
      +-- tbody
           |
           +-- tr
                |
                +-- td

A recursive transformer can visit every node without knowing the maximum tree depth beforehand.

44. Generic Recursive Transformation

const transformNode = node => {

    if (!node || typeof node !== "object") {
        return node;
    }

    // transform current node

    if (Array.isArray(node.children)) {

        node.children =
            node.children.map(transformNode);

    }

    return node;
};

The exact transformation logic depends on the task.

83. Benefits of the Contract

  • Transformations remain composable.
  • Responsibilities remain separated.
  • Intermediate specifications can be inspected.
  • DOM construction remains independent.
  • Deep specification trees can be transformed locally.
  • New middleware can be introduced without rewriting the DOM builder.

The core contract is simple:

A transformation receives a specification, changes only what it is responsible for, preserves the specification model, and returns a specification that the next stage can consume.

The God JSON is therefore not merely a static template. It is the structural specification that travels through the transformation pipeline. Columns, data, renderers, themes, and other middleware progressively enrich or modify that specification. Only after those transformations are complete does the generic recursive DOM builder materialize the resulting tree.
