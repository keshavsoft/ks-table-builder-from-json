1. Theme Architecture

Themes are deliberately kept separate from the main structural specification. 

God Spec
    |
    | structure
    |
    +------------------+
                       |
                       v
                  Theme Spec
                       |
                       | appearance
                       v
                  Transformed Spec

The God Spec describes what elements exist. The Theme Spec describes how those elements should look.

2. Why Themes Are Separate

A component should not need a completely different structural JSON specification simply because its appearance changes. 

                 Same God Spec
                       |
          +------------+------------+
          |            |            |
          v            v            v
        Light        Dark        Medium
        Theme        Theme        Theme
          |            |            |
          +------------+------------+
                       |
                       v
                  Final Spec

The structure remains the same while presentation can vary.

3. Theme Files

Themes can be maintained as separate JSON specifications. 

themes/
    |
    +-- dark.json
    |
    +-- extra-dark.json
    |
    +-- medium.json
    |
    +-- light.json
    |
    +-- extra-light.json
    |
    +-- index.js

The JavaScript index acts as the theme registry and resolver.

4. Theme Registry

The theme registry associates a theme name with its JSON specification. 

const themes = {
    "extra-dark": extraDarkSpec,
    "dark": darkSpec,
    "medium": mediumSpec,
    "light": lightSpec,
    "extra-light": extraLightSpec,
    "default": lightSpec
};

This allows application code to refer to a theme by a simple name. 

{
    inTheme: "dark"
}

5. Theme Resolution

Theme resolution determines which theme specification should actually be used. 

inThemeSpec
     |
     | if supplied
     v
Use supplied Theme Spec

otherwise

inTheme object
     |
     v
Use object directly

otherwise

inTheme / inThemeName
     |
     v
Theme Registry
     |
     v
Named Theme

otherwise

Default Theme

This provides flexibility without requiring the rest of the rendering system to know how the theme was selected.

6. Theme Resolution Contract

Conceptually: 

resolveThemeSpec({
    inTheme,
    inThemeName,
    inThemeSpec
})

The resolver returns a Theme Spec object.

From that point onward, the pipeline does not need to care whether the theme originated from a name, object, or default.

7. Theme Task

Theme application is exposed to the Table pipeline through a transformation task. 

createApplyThemeTask({
    inThemeSpec
})

The task returns a function that accepts the current specification. 

currentSpec
     |
     v
Theme Task
     |
     v
themedSpec

8. Theme Transformation

The Theme Task delegates the actual recursive transformation to applyTheme(). 

applyTheme({
    inSpec,
    inThemeSpec
})

The function walks the specification tree and applies the corresponding theme information.

9. Recursive Theme Application

The Theme Spec follows the structure of the main specification. 

God Spec                    Theme Spec

div                         div
 |                           |
 +-- toolbar                 +-- toolbar
 |                           |
 +-- table                   +-- table
      |                            |
      +-- thead                   +-- thead
      |
      +-- tbody                   +-- tbody
      |
      +-- tfoot                   +-- tfoot

Corresponding nodes can therefore be processed recursively.

10. Applying Classes

One of the primary purposes of the Theme Spec is supplying class attributes. 

{
    "tagName": "table",
    "attributes": {
        "class": "w-full bg-gray-900 text-gray-200"
    }
}

The theme transformation places the theme class information into the resulting specification. 

God Spec
    +
Theme Spec
    |
    v
Resolved Spec

11. Theme Application Does Not Create DOM

Theme application happens entirely before DOM creation. 

God Spec
    |
    v
applyTheme()
    |
    v
Themed JSON Spec
    |
    v
buildSpecElement()
    |
    v
DOM

This is a critical architectural boundary.

applyTheme() works with JSON objects. buildSpecElement() works toward DOM objects.

12. Example: Table Wrapper

Suppose the God Spec contains: 

{
    "tagName": "div",
    "attributes": {
        "class": "table-wrapper"
    }
}

The dark theme can provide: 

{
    "tagName": "div",
    "attributes": {
        "class": "table-wrapper space-y-3"
    }
}

The resulting specification can then be passed to the generic DOM builder.

13. Example: Dark Table

A dark theme specification may contain classes such as: 

table:
    bg-gray-900
    border-gray-700
    text-gray-200

thead:
    bg-gray-800
    border-gray-700

tbody:
    divide-gray-700
    text-gray-200

input:
    bg-gray-900
    border-gray-700
    text-gray-200

These are presentation decisions. The Table renderer does not need to embed them directly into its structural logic.

14. Theme and Pipeline

Theme is simply one transformation in the larger pipeline. 

God Spec

    v

This is why theme handling fits naturally into the middleware model.

15. Theme Does Not Own Structure

The theme should not become the source of structural decisions.

For example, a theme should not decide: 

Should the table have a footer?
Should serial numbers exist?
How many rows exist?
Which records are displayed?

Those decisions belong to other transformations or component logic.

16. Theme vs Data

Theme
    |
    +--> appearance
    +--> classes
    +--> visual presentation

Data
    |
    +--> records
    +--> values
    +--> state
    +--> UI-derived data

These concerns should remain independent.

17. Theme vs Columns

Theme
    |
    +--> how the column looks

Columns
    |
    +--> what the column represents
    +--> what control it renders
    +--> where it belongs

A theme can style a column without determining the column's business meaning.

18. Theme and Forms

The same concept applies to Forms. 

Form God Spec
      +
Form Theme
      |
      v
Form Resolved Spec
      |
      v
Recursive DOM Builder
      |
      v
Form DOM

The generic theme mechanism can therefore be reused for another component as long as its structural specification can be mapped to the theme specification.

19. Theme Structure Must Be Understandable

Because the current theme mechanism recursively processes corresponding nodes, the Theme Spec should remain understandable relative to the God Spec. 

God Spec
 |
 +-- div
 |
 +-- table
      |
      +-- thead
      +-- tbody
      +-- tfoot

Theme Spec
 |
 +-- div
 |
 +-- table
      |
      +-- thead
      +-- tbody
      +-- tfoot

Keeping the structures aligned makes the transformation easier to reason about.

20. Structural Drift

A mirrored tree introduces one important maintenance concern: structural drift.

If the God Spec changes substantially while the Theme Spec is not updated accordingly, corresponding nodes may no longer represent the same UI element. 

God Spec
    |
    +-- toolbar
    +-- table
         |
         +-- thead
         +-- tbody

Theme Spec
    |
    +-- toolbar
    +-- table
         |
         +-- tbody
         +-- thead

This is why the God Spec should be treated as a structural contract.

21. Why Keep the Current Model?

A mirrored Theme Spec is simple to understand.

The developer can visually compare: 

God JSON
Theme JSON

and see which structural node receives which classes.

A more abstract selector-based theme system could be introduced later if maintaining mirrored trees becomes difficult.

22. Possible Future Theme Strategies

If the current positional tree mapping eventually becomes difficult to maintain, alternative strategies could include:

  • semantic node names
  • stable identifiers
  • selectors
  • named slots
  • path-based mappings
  • component-specific theme tokens

These should be considered only when there is a concrete maintenance problem.

24. Theme Is Middleware

The most useful mental model is: 

Theme
   =
Specification Middleware

It receives a specification, modifies it, and returns another specification. 

Spec
 |
 v
Theme
 |
 v
Spec

This is the same fundamental contract used by the other transformation tasks.

25. Final Theme Mental Model

                 GOD SPEC
                    |
                    | structure
                    v
                THEME SPEC
                    |
                    | appearance
                    v
             THEME TRANSFORM
                    |
                    v
              RESOLVED SPEC
                    |
                    v
            RECURSIVE BUILDER
                    |
                    v
                   DOM

A theme does not build the UI. It transforms the UI specification so that the final DOM builder can build the UI with the desired appearance.
