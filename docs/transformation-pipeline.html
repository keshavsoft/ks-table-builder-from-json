1. What Is the Transformation Pipeline?

The transformation pipeline is the stage between the initial JSON specification and the final specification that is given to the DOM builder. 

God Spec
    |
    v
Transformation Pipeline
    |
    v
Resolved Spec
    |
    v
DOM Builder
    |
    v
DOM

The pipeline does not create DOM elements. It transforms the specification.

Pipeline input: Specification. Pipeline output: Specification.

2. The Core Contract

Every pipeline task follows the same basic conceptual contract: 

inSpec
   |
   v
Transformation Task
   |
   v
outSpec

In other words: 

Specification -> Specification

This makes the tasks composable.

3. Why Use a Pipeline?

A Table has many independent concerns. 

Theme
Header
Body
Footer
Serial
Columns
Actions
Custom UI

Putting all of these concerns into one large rendering function would make the renderer difficult to understand and maintain.

The pipeline allows each concern to become an independent transformation.

4. Pipeline as Middleware

The pipeline can be understood as middleware over the specification.

There are two separate operations.

Building the pipeline and running the pipeline are separate responsibilities.

7. buildTablePipeline()

The Table pipeline builder receives configuration and determines which tasks should participate. 

buildTablePipeline({
    inThemeSpec,
    inShowHeader,
    inShowBody,
    inShowFooter,
    inShowSerial,
    inCustomTasks
})

It creates an initially empty array: 

const pipeline = [];

Tasks are then added to this array in a defined order.

8. Theme Task

If a theme specification is available, the Theme Task is added to the pipeline. 

if (inThemeSpec) {
    pipeline.push(
        createApplyThemeTask({
            inThemeSpec
        })
    );
}

This means theme application is optional.

When a theme exists, the specification is transformed before subsequent tasks execute.

9. Header Task

The Header Task controls the presence or configuration of the table header. 

pipeline.push(
    createHeaderTask({
        inShowHeader
    })
);

The task operates on the specification rather than directly creating or destroying DOM elements.

10. Body Task

The Body Task handles the body portion of the table specification. 

pipeline.push(
    createBodyTask({
        inShowBody
    })
);

The resulting specification determines what reaches the DOM builder.

11. Footer Task

The Footer Task handles the footer portion of the specification. 

pipeline.push(
    createFooterTask({
        inShowFooter
    })
);

Again, this is a specification-level decision.

12. Serial Task

The Serial Task handles the Table's serial-number column transformation. 

pipeline.push(
    createSerialTask({
        inShowSerial
    })
);

The task is concerned with the Table specification and its representation of the serial column.

13. Custom Tasks

External transformation functions can be appended to the pipeline. 

if (
    Array.isArray(inCustomTasks) &&
    inCustomTasks.length > 0
) {
    pipeline.push(...inCustomTasks);
}

This is an important extension point.

New behavior can be introduced without modifying the generic pipeline runner.

14. Complete Pipeline Builder

export const buildTablePipeline = ({
    inThemeSpec,
    inShowHeader = true,
    inShowBody = true,
    inShowFooter = true,
    inShowSerial = true,
    inCustomTasks = []
}) => {

    const pipeline = [];

    if (inThemeSpec) {
        pipeline.push(
            createApplyThemeTask({
                inThemeSpec
            })
        );
    }

    pipeline.push(
        createHeaderTask({
            inShowHeader
        })
    );

    pipeline.push(
        createBodyTask({
            inShowBody
        })
    );

    pipeline.push(
        createFooterTask({
            inShowFooter
        })
    );

    pipeline.push(
        createSerialTask({
            inShowSerial
        })
    );

    if (
        Array.isArray(inCustomTasks) &&
        inCustomTasks.length > 0
    ) {
        pipeline.push(...inCustomTasks);
    }

    return pipeline;
};

15. runPipeline()

The generic runner executes the pipeline sequentially. 

export const runPipeline = ({
    inSpec,
    inPipeline = []
}) => {

    return (inPipeline || []).reduce(
        (currentSpec, taskFn) => {

            if (typeof taskFn === "function") {
                return taskFn({
                    inSpec: currentSpec
                });
            }

            return currentSpec;

        },
        inSpec
    );
};

16. How reduce() Fits the Pipeline

The reducer's accumulator is the current specification. 

inSpec
  |
  v
currentSpec
  |
  +--> task 1
  |
  v
currentSpec
  |
  +--> task 2
  |
  v
currentSpec
  |
  +--> task 3
  |
  v
finalSpec

Therefore the accumulator is effectively the specification travelling through the middleware chain.

18. Tasks Are Functions

A task is simply a function that receives an object containing inSpec. 

({ inSpec }) => {
    // transform specification
    return newSpec;
}

This small contract is what makes the pipeline generic.

19. Task Factory Pattern

Table tasks are created through factory functions. 

createHeaderTask(...)
createBodyTask(...)
createFooterTask(...)
createSerialTask(...)
createApplyThemeTask(...)

The factory receives configuration and returns the actual transformation function. 

configuration
     |
     v
Task Factory
     |
     v
Configured Task Function

20. Why Task Factories Are Useful

Consider: 

createHeaderTask({
    inShowHeader: false
})

The resulting function already has access to the required configuration.

The pipeline runner only needs to execute it. 

Runner
  |
  v
taskFn({ inSpec })

The runner does not need to pass every Table configuration option to every task.

26. Pipeline Order Is a Contract

The order of tasks matters. 

Task A
  |
  v
Task B
  |
  v
Task C

Task B sees the result of Task A. Task C sees the result of Task B.

Therefore changing pipeline order can change the final result.

27. Example of Order Dependency

Suppose a later task expects a node to already exist. 

Task A
    |
    +---- creates / inserts specification node
    |
    v
Task B
    |
    +---- modifies that node

Reversing them could cause Task B to have nothing to modify.

Pipeline order should therefore be intentional.

35. What the Pipeline Should Not Do

The pipeline should not become a second DOM engine.

Avoid making transformation tasks responsible for:

  • document.createElement()
  • appendChild()
  • querySelector()
  • DOM event registration
  • direct DOM mutation

Those responsibilities belong to the DOM layer.

36. What the Pipeline Should Do

The pipeline should perform specification-level operations such as:

  • adding nodes
  • removing nodes
  • changing attributes
  • changing classes
  • changing properties
  • changing children
  • inserting UI columns
  • changing component structure

37. Pipeline as a Composition Mechanism

43. The Pipeline Is Not the Renderer

These are different responsibilities. 

Pipeline
    =
Transforms specification

Renderer
    =
Coordinates component rendering

DOM Builder
    =
Materializes specification

Keeping these boundaries clear prevents responsibilities from leaking between layers.
